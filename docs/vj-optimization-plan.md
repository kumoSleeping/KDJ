# 旧 VJ 定位优化方案（待统一实施）

本轮只实施新实时 VJ 面板及其独立会话；旧混接编辑器不改匹配算法、阈值、持久项目或已有缓存格式。之前补充的计时日志继续保留。本文是供开发讨论的方案，不表示优化已经完成。

实施状态：下表 1–8 项均**尚未实施**。自本文写入以来，`crates/kdj-analysis` 的旧混接定位代码没有相应改动；表中“预期作用”只是计划，不是已取得的收益。实时 VJ 的当前识别与跟随策略以 `live-vj-following.md` 和下文“当前实时识别策略”为准。

## 实测依据

见 `vj-alignment-performance.md`：同一视频与两段录音，全冷 14.427 秒；参考特征已有、新视频首次分析 5.254 秒；全部特征已有仍需 4.320 秒。开发构建，四种条件各一次，不能等同于发布版或大素材库指标。这些是旧混接编辑器的离线定位耗时，不是实时 VJ 的端到端延迟。

## 从新实时面板可复用的设计

- 素材身份与时间线编排分离。换序、改 Set 名称不重做音频特征；源文件改变必须失效。当前实时索引的键包含整个 Set 文档，因此换序或改名仍会用已缓存的区块特征重建整套常驻索引（不重新解码），这部分成本与素材实际变更应分开测量。
- 单会话、可取消、固定内存预算。不能通过无限并发把墙钟时间降下来，却抢占 DJ 音频线程。
- 保留实际分阶段时间：准备素材、解码/特征、候选扫描、精细验证、输出首帧。不要把结果缓存命中当成新素材识别速度。
- 当前实时实现没有“下一项优先”或后台发现份额：锁定期间只在当前位置附近做局部跟踪，失锁后才对整套 Set 做逐速度档地标检索（见下文）。这条实时调度策略不移植到旧编辑器：旧编辑器需要完整对应，不能漏掉后面的更优或冲突候选。
- 命中后跟踪位置；无证据不清空画面。此为实时输出策略，不改变旧项目剪辑结果。

## 当前实时识别策略（以代码为准）

以下按 `src-tauri/src/live_vj/runtime.rs`、`feature_input.rs`、`crates/kdj-analysis/src/alignment/live.rs`、`live_index.rs` 核对。早先“8 秒证据窗及连续确认”的描述已不适用，代码中没有该等待。

- 查询窗：固定取最近 550 ms 的增量特征（本机采集与蓝牙接收相同），不因歧义延长；分析层只接受 0.35–3 秒的查询。识别循环约每 125 ms 取一次最新音频，采集不等待识别，不积压旧查询。
- 接受条件：声学校验结果 `matched || supported` 即发布位置，不再有上层门槛、跨候选否决或连续确认。阈值保持在分析层：`matched` 要求得分 ≥ 0.72、最弱窗 ≥ 0.60、与次选差 ≥ 0.10；`supported` 要求检索支持 ≥ 0.65、得分 ≥ 0.62、最弱窗 ≥ 0.50、与次选差 ≥ 0.14。局部跟踪路径另在预测位置两侧 0.4–3.2 秒检查相似位置，差距不足 0.10 时判为未通过。分析层对 `supported` 的原因文字仍写作“待连续确认”，这是遗留措辞，运行时直接采用该结果。
- 复核策略：最近一次被接受的证据不超过 2 秒时，每轮只在预测位置附近做局部跟踪，通过则不再做全 Set 检索。局部未通过的同一轮立即转为救场检索；超过 2 秒没有被接受的证据即标为失锁，保留当前画面。输入断流或采集代次变化时清空速度估计并从头检索。
- 速度搜索：先按当前速度（无锁定时为 1×）检索，再由近到远尝试 0.80–1.25× 的 19 个速度档（步长 0.025）。每档对整套 Set 做地标检索，按排名逐块声学校验，首个通过即采用，不等待其余速度档或素材。每完成一档检查 125 ms 软预算，到点就让出，下一轮用新音频从剩余速度档继续；采用结果或扫完全部档后才从头开始。125 ms 是档间让出点，不是单档耗时、单轮耗时或端到端切入延迟。
- 跟随时钟：被接受的观测按最多 32 点、3 秒的线性拟合估计基准速度，斜率限制在 0.80–1.25×；同一录音内位置跳变不足 2.5 秒时沿用当前锁定继续校正，否则视为新的跳转。
- 内存：常驻地标索引预算 128 MiB，区块特征缓存与检索投票工作区各按 32 MiB 约束。这些是局部预算，不是整机或 WebView 的峰值上限。

## 新实时链路的验证边界

本轮在隔离数据目录、真实 macOS Tauri 窗口中验证了系统音频匹配视频、匹配音频后绘制歌词可视化、两者切换、独立窗口和当前屏幕全屏，以及输入停止后继续播放。Set 的曲库拖入、排序和重启读取也已验证；没有连接外接屏，未验证实际跨屏输出。该记录未注明对应哪一版识别策略，不能视为对上述 550 ms 短窗策略的复验。

单视频场景曾显示约 10.9 ms/轮，这是单次界面观察值，不是端到端延迟或统计分位数。素材索引准备、采集积累、计算和首帧等待必须分别测量。变速、重混、Windows 真机捕获和大 Set 压力场景尚未完成，不能由这一观察值推算它们的表现。

实时缓存目前独立，采用 8 kHz 分析、300 秒核心块并在两侧各留最多 8 秒重叠区；以后与旧流程共享时，必须将采样、重叠、特征版本等参数纳入资产身份，不能直接把两个流程的缓存文件互换。

## 平台范围：已实现 / 已验证

- macOS：已实现 Core Audio Tap（14.2 及以上）、ScreenCaptureKit 系统混音、原生声卡／麦克风输入、外接屏优先的画面「自动」和蓝牙接收。已验证范围仅限上一节记录的真实窗口验证，未连接外接屏；Core Audio Tap 的实际 Master／Cue 隔离未验证。
- Windows：已实现 WASAPI 回环（默认播放设备及各输出端点）、「第二路 Master · 电脑声卡」、WebView2 解码和蓝牙接收。WASAPI 捕获标志通过根 `Cargo.toml` 的 `[patch.crates-io]` 使用打补丁的 `vendor/cpal-0.18.1`（PR #31，issue #26），已在代码中生效，不再是待定事项；但该补丁只做过非 Windows 主机上的 `x86_64-pc-windows-msvc` 交叉 `cargo check` 和单元测试，未在 Windows 真机运行。采集、解码、静音恢复、默认设备切换、热拔插和 ASIO 场景均未验证。
- Linux：已实现以系统默认录音输入作为「自动」、原生录音输入设备列表，以及按显示接口名（eDP／LVDS／DSI）识别内置屏；没有回环设备列表，不支持蓝牙接收。未验证。
- Android：实时 VJ 模块在 `src-tauri/src/lib.rs` 中仅为桌面编译（`#[cfg(desktop)]`），Android 不提供该功能；蓝牙发送也只支持 macOS 和 Windows。无可验证范围。

## 实施顺序与验收边界

先做 1–3 的等价计算优化，再做 4–5 的资产缓存优化，最后考虑 6–8 的检索结构。每组修改只运行已有的相关检查，不新增测试脚本或夹具；使用同一真实素材和隔离数据目录复测并清理临时产物。

验收同时看：墙钟耗时、CPU 时间、峰值工作集/缓存大小、取消响应、音频负载下的稳定性、匹配结果是否变化。任何降低准确度或缩窄检索范围的方案都须单独说明，不能混进等价性能优化。旧 `vj-projects.json` 不用于实验性写入。
