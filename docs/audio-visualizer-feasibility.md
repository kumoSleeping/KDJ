# KDJ 音频可视化视频实施计划

更新日期：2026-09-21  
状态：实施中。第一步的导出内核、macOS 真实编码/失败回退与 Canvas 对照已通过首轮验证；完整首版尚未交付，正式 UI、Windows 真机及 Tauri 壳验收仍待完成。具体落地代码、测试、样片和后续边界见 [第一批实施记录](audio-visualizer-implementation.md)。本文替代上一版报告中的平台范围、技术分工和排期；不再提供工期或工作量估算。

## 1. 本版范围

仅实现 Windows 和 macOS，Linux 与 Android 本轮不做。沿用 Rust + Tauri 架构，充分复用项目现有 FFmpeg 工具管理、媒体合成、编码加速与导出任务能力。

目标流程：曲库选择一首歌 → 右键“生成可视化视频” → 打开右侧独立“可视化”面板 → 自动带入封面与曲目信息 → 调整画面 → 导出 MP4。

首版提供一个完整的“双栏弧形频谱”模板，以参考图的构图、唱片、透明频谱与分层律动为重点。默认导出 1080p、30 fps；支持 16:9 与接近参考图的宽屏构图。60 fps 待实际链路验证后开放，不作为首版完成条件。

至少一张、最多两张图片；默认歌曲封面。单图可同时用于左右两栏和唱片，分别保存位置与裁剪参数；第二张默认用于右栏。无有效封面时通过 `+` 添加图片，加载成功后才允许生成。图片空区保持空白。

首版输入为可读取的完整本地音频，包括已下载歌曲。在线预览地址或官方嵌入播放器不直接视为可导出的完整音频源。工程固定引用所选歌曲，切换全局播放歌曲不会替换工程内容。

## 2. 技术分工：FFmpeg 承担通用处理，KDJ 实现独有视觉

不再把“前端逐帧绘制整张 1080p 画面后全部传给后端”设为首选方案。优先让 FFmpeg 从源图片和音轨直接完成通用处理，只为定制效果提供必要的动画参数、蒙版或透明图层。

| 内容 | 负责方 | 实现方向 |
| --- | --- | --- |
| 图片缩放、裁剪、旋转、镜像、柔化 | FFmpeg 导出；Canvas 交互预览 | 共用坐标、裁剪与变换参数 |
| 左右图片、圆盘与方形封面叠放 | FFmpeg | 使用图片、几何蒙版与滤镜合成 |
| 弧形分界 | KDJ 生成几何蒙版，FFmpeg 合成 | 蒙版由曲线参数生成；参数未变时复用 |
| 音频频带、包络和起音分析 | 现有 Rust 分析模块 | 复用流式解码与 FFT，生成紧凑时间序列 |
| 沿弧线伸展的双向频谱 | KDJ 定制绘制 | 优先输出覆盖必要区域的透明动态图层，交给 FFmpeg 叠加 |
| 普通直线频谱与波线 | 优先验证 FFmpeg 现成滤镜 | 仅在透明度、样式与预览一致性符合要求时采用 |
| 唱片旋转 | FFmpeg 导出；Canvas 预览 | 使用歌曲时间计算角度，方形封面独立遮挡 |
| 各图层独立律动 | KDJ 计算运动曲线，FFmpeg 执行适用变换 | 使用统一时间基准；验证滤镜表达式或命令更新的适用范围 |
| 文字、歌词、光点 | KDJ 布局和时间计算，FFmpeg 合成 | 静态文字复用纹理，动态部分按需绘制，保证字体和时间一致 |
| 音轨处理、色彩转换、视频编码、MP4 封装 | FFmpeg | 复用现有编码能力和成品校验 |
| 工程、任务、进度、取消和结果提交 | KDJ Rust 后端 | 复用现有生命周期管理 |

FFmpeg 已有 `scale`、`crop`、`rotate`、`overlay`、`showfreqs`、`showwaves` 等滤镜；实际可用性按用户安装的构建探测，不能假定所有工具包启用了同一组滤镜。[FFmpeg 官方滤镜文档](https://ffmpeg.org/ffmpeg-filters.html)

参考图中的曲线双向频谱、透明原色与独立律动仍需定制，不能用默认频谱滤镜替代后就算完成。FFmpeg 内置频谱若无法与预览共用相同结果，则这部分统一由 KDJ 绘制。

透明图层保持真正的 alpha，不通过删除黑色来做透明，避免误删图片本来的黑色细节。基础图像始终保持原色，小频谱只绘制柱体和轮廓，不绘制黑色山形填充，也不因强拍给原图加黑。

## 3. Windows / macOS 硬件加速

沿用 `crates/kdj-server/src/compositions/acceleration.rs` 的现有能力，针对新输入布局做适配，不另起一套编码后端。

| 平台 | 优先使用的现有编码能力 | 回退 |
| --- | --- | --- |
| macOS Apple Silicon / Intel | FFmpeg `h264_videotoolbox`，通过实际编码探测确认可用 | `libx264` 软件编码 |
| Windows | FFmpeg `h264_nvenc` / `h264_qsv` / `h264_amf`，按已有自动选择与用户设置探测 | `libx264` 软件编码 |

这里首先保证的是硬件视频编码。图片滤镜、透明合成与自绘图层仍可能运行在 CPU；不能把启用硬件编码描述为所有画面处理都由 GPU 完成。只有实际测量证明有效且平台可用时，再采用相应硬件滤镜，避免 CPU/GPU 来回搬运反而变慢。

复用当前自动探测、失败回退与进度机制。已有加速模块对参数布局有明确限制，新输入选项及管道必须适配后才能进入硬件路径。若硬件导出失败，需要从确定的时间与输入重新生成整段，自绘管道也必须可重建，不能拿已消费完的输入直接软件重试。

沿用项目现有 FFmpeg 依赖和安装配置，不随 KDJ 重复打包一套工具，也不引入 FFmpeg WASM。缺少必要能力时复用现有媒体工具设置入口，显示具体缺项。

## 4. 右侧面板与画面配置

| 分组 | 首版内容 |
| --- | --- |
| 预览 | 播放、暂停、跳转；直接拖动图片调整焦点 |
| 图片 | 一至两张；左右独立平移、缩放、旋转、镜像、替换与交换 |
| 构图 | 画布比例、左右比例、弧线位置与弯曲程度、背景柔化 |
| 唱片 | 隐藏、单圆盘、方形封面遮挡圆盘；位置、大小、转速、方向 |
| 频谱 | 弧形主频谱、小频谱；柱状/线条/平滑轮廓，配色、灵敏度、平滑与长度 |
| 律动 | 总强度与各层强度、低音响应、回弹速度；轻量光点与闪光开关 |
| 文字与歌词 | 标题、艺人、专辑的显隐与编辑；歌词开关、滚动/逐行、翻译、字号、位置和时间偏移 |
| 输出 | 名称、目录、画布尺寸、质量、编码设置、生成、取消、进度与打开结果 |

“歌词轮型”暂按轮播/滚动理解；真实逐字时间存在时才逐字高亮，不编造逐字时间。没有歌词仍可生成视频。

默认使用合理预设，细项折叠。图片总数最多两张，圆盘与方形封面复用已有素材，不再增加第三张图片入口。不加入自动抠图、模型下载、通用关键帧时间线或模板市场。

控制样式遵守 KDJ 现有约定。浮动预览沿用 `FloatingVideoControls`、`FloatingVideoScrub` 和 `kd-pip-float`；涉及视频播放、成品预览与跳转的路径继续使用共享调度层。

## 5. 实施顺序与每步交付

### 第一步：打通最小导出链路

- 建立统一场景参数：画布、图片变换、弧线、唱片、频谱与时间。
- 用一张封面和一段音频验证 FFmpeg 的图片处理、旋转、透明图层叠加、音轨合入与 MP4 输出。
- 验证 Mac / Windows 的现有硬件编码路径及软件回退。
- 比较 Canvas 预览与导出对应帧，确认 alpha、裁剪、旋转中心与颜色一致。
- 确认混合方案的自绘图层传输和滤镜开销；只有必要时才采用整帧自绘回退。

交付结果：可播放的真实样片，明确最终导出管线。这个阶段不以效果演示代替编码与同步验证。

### 第二步：接入歌曲与右侧面板

- 增加单曲右键入口、独立可视化面板和状态。
- 自动获取封面、曲名、艺人与歌词资料。
- 完成最多两张图片、独立调整焦点、替换、交换与恢复。
- 保存可视化工程；绑定曲目和素材签名，支持恢复及基本撤销。
- 预览使用现有音频播放时钟，暂停和跳转统一定位。

交付结果：从歌曲进入面板，默认构图可用，调整后能保存恢复。

### 第三步：完成参考图主体效果

- 绘制弧形双向频谱、彩色细线和点列。
- 完成两种唱片模式与透明小频谱。
- 用低频、响度、起音分别驱动左右图片、唱片和边界，设置不同方向、相位、强度与回弹。
- 预计算或按固定步长生成运动曲线，保证跳转与导出结果可重复。
- 计算图层移动、缩放与旋转的裁剪余量，避免震动露边。
- 加入克制的星点与光斑；文字尤其歌词保持易读。

交付结果：主体构图与参考图接近，图层有独立律动，图片不被动态黑底覆盖。

### 第四步：完成歌词、文字与整曲输出

- 接入现有歌词缓存、翻译和时间偏移。
- 处理长标题、中日韩字体、换行、双语与无歌词情况。
- 用同一时间轴生成图片运动、频谱与歌词，明确 FFT 窗中心及编码延迟。
- 完成整曲输出、进度、取消、错误显示与结果打开。
- 复用现有临时目录、文件签名校验、输出校验和原子提交机制。
- 导出不依赖屏幕录制，也不要求用户完整播放一遍歌曲。

交付结果：从一首歌到完整视频的首版闭环。

### 第五步：验收后交付首版

- 在真实 Tauri Mac / Windows 壳中验证预览与输出。
- 检查单图、双图、横图、竖图、透明立绘及不同曲风。
- 检查开头、中段、结尾的音画同步、歌词同步与最终时长。
- 验证最小化、切换面板、素材变化、取消、磁盘空间不足和编码失败。
- 检查原色、透明边缘、文字清晰度、硬编与软编输出。
- 对比安装包与前端产物，继续满足现有体积门禁。

交付结果：可在 Windows 和 macOS 使用的完整首版，以及已知限制说明。

## 6. 性能、体积与实现约束

- 计划不增加前端运行时依赖，不引入大型渲染引擎、模型、字体包或默认大图素材。
- 音频分析复用现有 Rust 流式解码与 FFT；仅对需要生成的歌曲建立可清理缓存。
- FFmpeg 直接读取基础图片和音轨；自绘数据只传必要区域，实际带宽须测量，不能因为采用混合合成就假定开销消失。
- 静态蒙版与文字复用；动态透明图层采用有界二进制通道，禁止整帧 JSON/Base64，不落盘保存整曲 PNG 序列。
- 音画都按确定时间生成；设备较慢时增加导出耗时，不靠丢帧缩短视频。
- 滤镜和编码均服从现有资源调度；硬编不等于零 CPU 占用。
- 本地生成不调用云渲染或生成式 AI，不增加按次收费或生成额度。
- 复用现有 FFmpeg 来源和许可记录；不复制参考图中的专辑素材、Logo 与字体作为内置资源。
- 前端懒加载减少首屏加载，但总安装包仍按现有门禁验收，不预先放宽预算。
- 后续验证只覆盖相关 TypeScript、Rust 模块及目标平台，不为计划阶段运行构建或启动应用。

## 7. 首版完成条件

1. 歌曲右键可以打开独立右侧面板，默认带入有效封面。
2. 至少一张、最多两张图片；两栏可以独立调整重点。
3. 弧形频谱、透明小频谱、两种唱片模式和分层律动完整可用。
4. 歌词可选，无歌词不阻断输出。
5. 能导出带完整音轨的 MP4；同一时刻预览与导出构图、频谱、运动和歌词一致。
6. Windows / macOS 硬件编码经过实际探测，失败后可可靠软件回退。
7. 取消和失败不会遗留伪成品，任务不会无限堆积帧或占用内存。
8. 安装包继续满足项目既有体积控制。

本轮只修订此计划。Linux、Android、工期与工作量估算均不纳入本版。
