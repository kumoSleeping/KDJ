# 03 · 分析管线（BPM / 调号 / 能量）脱离 numpy 与 ffmpeg

`crates/kdj-analysis`：解码 + DSP 原语 + tempo + key + loudness + 总入口。
47 个单元测试，外加**和 Python 版在用户真实曲库上的逐字段对拍**。

## 结果：40 首真机对拍

样本取自 `/Users/kumo/git/djay/`（每 19 首抽 1 首，覆盖各个 gig-set 目录）：

| 指标 | 一致率 |
| --- | --- |
| **调号（camelot）完全一致** | **39/40 = 98%** |
| **能量分级完全一致** | **40/40 = 100%** |
| RMS 最大偏差 | **0.050 dB** |
| BPM 完全一致（差 < 0.05） | 18/40 = 45% |
| BPM 差 < 1 | 30/40 = 75% |
| BPM 同族（含 ×2 / ×½ / ×1.5 等倍频关系） | 36/40 = 90% |

调号和能量可以认为是**完全对齐**的。BPM 有 10% 落在"不同族"，
下面单独说。

## 坑 1：RMS 稳定低 2.97 dB —— ffmpeg 的单声道下混不是取平均

第一轮对拍，12 首里 11 首的能量分级都比 Python 版低 1 档。
查 `rms_db` 发现差值是个**常数**：−2.96、−2.93、−2.94、−2.97…… 全部 ≈ −3.01 dB。

常数差 = 纯增益问题，而不是算法问题。−3.01 dB 正好是 1/√2。
再看 `peak_db`：Python 报的是 **+5.08 dB**（超过满刻度！），我报的是 0.00（被 1.0 夹住）。

答案是 ffmpeg 的 `-ac 1` 用的是**能量守恒的 -3dB 声像律**（每声道 ×1/√2），
不是简单的 `(L+R)/2`。所以下混要写成：

```rust
let gain = 1.0 / (ch as f32).sqrt();   // 不是 1.0 / ch
```

改完之后 RMS 偏差从 −2.97 dB 掉到 ±0.01 dB，能量分级 40/40 全中。

这条差异对 BPM 和调号毫无影响（那两条都先按峰值归一），
但 `energy` / `rms_db` / `peak_db` 是直接进曲库、直接显示给用户的字段。

## 坑 2：线性插值重采样把高频吃掉了

一开始重采样图省事用线性插值。44.1k → 22.05k 时，线性插值等价于一个很钝的低通，
高频被大幅衰减 —— 起音包络的形状跟着变，BPM 的倍频判定就容易和 Python 分道扬镳。

换成 16 taps 的加窗 sinc（Blackman 窗），通带做平。测试
`sinc_resampling_keeps_a_tone_at_full_amplitude` 钉住这一点：
2 kHz 正弦过一遍降采样后峰值必须还在 0.97 以上。

副作用：sinc 核在信号两端会被截断+夹取，边缘几个样本必然有过渡。
这是加窗 sinc 的固有性质，测试只看中段。

## 关于 BPM 的 10%：这是算法本身的性质，不是移植缺陷

剩下 4 首不同族的：

```
 92.49 ->  123.46  ×1.335   ダラシナイEveryday
103.38 ->  116.37  ×1.126   marble heart
130.61 ->   97.81  ×0.749   笑門来福
 95.76 ->  128.01  ×1.337   わたしの一番かわいいところ
```

两首是 ×4/3（三连音/shuffle 歧义），一首 ×3/4，一首 ×9/8。
**两边的 `bpm_confidence` 都是 1.0** —— 也就是说双方都找到了一个完全规整的节拍网格，
只是选了不同的倍数。

Python 版自己的注释里已经写明了这个算法的天花板：

> 试过给非二倍关系（×1.5 / ×⅔）打 0.8 折…… 实测无效：误判没修好，
> 与 librosa 的一致率反而从 31% 掉到 29%。结论是问题不在倍率集合，
> 而在梳状分本身对真实音乐区分度太低。

梳状分在这些曲子上本来就是**接近平局**，任何一点数值扰动（哪怕只是
解码器 40 ms 的时长差导致分析窗错开一点）都会让排序翻转。
所以这 10% 不是"Rust 版算错了"，是这个算法在这些曲子上本来就没有稳定答案。

### 对用户曲库的实际影响：用户选择直接重算

最初的设计是"绝不重算已分析的曲目"，靠 `analyzed_at IS NULL` 把影响压成零。
后来用户明确放行了：

> 其实可以把本地的清理一下，然后重算都是没有问题的。
> 已经算好的其实都无所谓，反正现在新算法应该也挺快的。

**结论反而更干净**：与其让库里一半是 Python 算的、一半是 Rust 算的
（两套算法的 BPM 在 10% 的曲子上不一致，混在一起才真的没法比），
不如整库用同一套算法重算一次。

- 后台自动分析仍然默认只挑未分析的——那是**省时间**，不再是安全约束。
- 「重新分析全部」是正当的用户操作，UI 上要有入口。
- 耗时：40 首约 100 秒（2 worker），全库 1379 首约 30 分钟。

## 顺带修好的一个真缺陷：不装 ffmpeg 也能分析

Python 版的解码是起 ffmpeg 子进程，所以
**没装 ffmpeg 的用户连 BPM 都分析不了**（`docs/05` 的「已知边界」里记着这条）。

Rust 版用 symphonia 内建解码 mp3 / flac / m4a / ogg / wav，开箱即用。
这同时也是上安卓的必要条件——安卓上没法 spawn 任意可执行文件。

B 站视频混流仍然需要 ffmpeg（和 v0.1.0 一致），安卓走 durl 单流绕开。

## 对拍怎么复现

```bash
# Rust 侧
cargo run --release -p kdj-analysis --example golden -- <清单文件>
```

清单文件是一行一个路径。**不要在 shell 里展开文件名**——
曲库文件名里全是空格、逗号、全角括号，`$(cat ...)` 必然被切碎
（第一次就是这么把 12 首切成了 30 条乱码路径，两边都在分析不存在的文件，
输出一片 `null` 还看不出哪里错）。

Python 侧对应的脚本在对拍完成后已删除，需要时按同样的接口重建：
读清单 → `analyze_file(path, duration_limit=240.0)` → 输出同构 JSON。

## 性能

40 首（每首分析 240 秒窗口）Rust 用了约 100 秒，Python 用了约 6 分钟。
快 3~4 倍，且没有子进程开销。
