# 万首曲库：按位置加载与悬浮滚动条

## 实现

本地曲库读取完整的有序 ID 清单，再按视口读取歌曲摘要。滚动条的长度和位置由完整清单决定，跳到末尾不会顺序加载前面的歌曲。旧的 `/api/library/tracks` 分页接口继续保留。

- `GET /api/library/tracks/index` 接收原有筛选、文件夹及主副排序参数，返回 `{ track_ids, total }`。不接受分页游标；排序、空值和同值顺序与原分页查询共用实现。
- 摘要每批最多 500 首（服务端上限），最多两个并发请求，当前视口优先；其中一个请求位在后台从视口向外补齐整份清单。内存保留最多 50000 首，超出后按 LRU 淘汰并保护当前预取范围。
- 查询版本隔离索引、摘要和错误；后台事件以 ID 回填，250 毫秒合并、最长等待 1 秒，不再排序和裁剪整个前端歌曲数组。请求 15 秒超时。失败或超时的批次不是终态：其中的行按 1、2、4、8、15 秒的间隔自动重新排队，期间保留错误提示和重试按钮，加载成功后提示自动清除；五次之后才停下，等待重试按钮、涉及这些行的后台事件，或视口再次需要它们。
- 全选、Shift 区间选择、键盘/MIDI 浏览、下一首播放、定位和批量操作使用完整顺序。详情独立于摘要缓存。
- 虚拟窗口和实际滚动位置同时限制在有效范围；后台变更保持顶部歌曲 ID 和行内偏移，切换查询回顶部。旧会话的像素位置仍可恢复。
- 滚轮、触控板和触摸滚动由 WebView 的滚动线程执行，页面不取消 wheel 事件。页面接管滚轮（拦下 wheel、在动画帧里改写位置）可以保证位置和行同帧画出，但滚动位置只能跟着主线程的帧前进：窗口提交一慢，滚动本身就卡，开发版尤其明显。现在主线程忙时滚动照常，代价是页面拿到位置时它已经在屏幕上了，行要靠下面几条追上。
- 所有来源的滚动（滚动线程的，以及拖滑块、键盘、定位这些页面自己执行的）都走容器的 scroll 事件，一帧合并一次，并在这一帧内用 `flushSync` 提交对应的行。
- 渲染窗口按 8 行一步移动，一步之内的滚动帧不进 React。窗口的形状由滚动节奏决定（`libraryScrollPace`，速度按约 100 毫秒平滑，单次滚轮格不算快）：
  - 停着或慢滚：视口前后各两屏。
  - 快滚（超过 3 px/ms，降到 1.2 px/ms 以下才退出）：后方一屏、前方三屏，行数不变。
  - 一帧走过两屏以上（拖滑块，或页面卡了一下）：只渲染落点和它前方一屏。
  - 滚动线程连续两帧都甩开页面两屏以上：按上一帧走过的距离提前渲染，最多八屏。只对滚轮/触摸之后 300 毫秒内的滚动这样做；页面自己执行的滚动位置是准的，不预测。
  - 140 毫秒没有新的滚动帧算停稳，窗口回到前后各两屏。
- 行是记忆化的组件，交互处理函数的身份不变：窗口移动只渲染新进来的行，留在窗口里的行整行跳过。
- 快滚途中挂载的行只画文字和已经缓存的封面，不发封面请求，不画评分和能量条；滚动慢下来或停稳后补全。已经画全的行不会退回去。
- 数据在渲染前一屏开始请求。待下载行同样虚拟化。
- 封面保留四个并发请求及 512 张缓存目标；取消的任务不能再被复用，旧任务不能清掉同键的新任务。网络/服务端临时失败最多重试两次，404 音频封面不轮询。可视范围内的请求优先；窗口移动后由表格统一调整等待中请求的优先级，行不为此重渲染。行挂载时先同步读取已有结论：缓存里有封面就直接画，已知没有封面就直接画唱盘，未知时格子留空，不再先画唱盘再换成封面；“没有封面”只是首帧提示，每次挂载仍会向服务端确认。

## 滚动条

曲库使用独立悬浮滑块，原生轨道隐藏，不为轨道留出布局空间。横向位于底边，纵向位于右边；滑块贴边、常驻可见，默认 6 像素，悬停及拖动时 8 像素，透明命中范围为 14 像素。最短滑块 44 像素。

仅滑块响应拖动，轨道区域不拦截歌曲交互；滚轮、触控板和触摸继续走原滚动容器。滑块支持方向键、Home/End、PageUp/PageDown、焦点样式及减少动态效果设置。滑块位置直接更新 DOM，不通过 React 每帧重绘表格。

## 自动验证

- `npm run test:library`：请求竞态、超时与重试、远跳、缓存上限、封面取消与重试、滚动条几何，以及真实 React 表格和状态模块的 JSDOM 测试。
- `npm run typecheck`。
- `cargo test -p kdj-library --lib library_index_`：完整索引与分页在主副排序/筛选下顺序一致，以及一万条数据库记录的直接末尾摘要查询。
- `cargo check -p kdj-server --lib`。

桌面 CI 已接入前端定向回归。测试使用内存数据或内存数据库，不生成歌曲、截图或临时项目。

## 玩家实机验收

自动验证不代表 Tauri 帧率达标。此变更尚未记录真实 Tauri 的修改前后帧率；本项保持待验收。

后端已修改，实机检查前需完整重启 Tauri 开发会话。检查同一万首文件夹：

1. 滚轮/触控板连续快滚（含惯性）、拖竖向滑块到末尾、横向拖到最后一列，再分别返回。滚动手感（惯性、到边停止）应与发行版一致，不随主线程忙闲变化；表格主体在主线程不被长时间占用时不应露白。快滚途中新进来的行可以只有文字，慢下来后封面、评分和能量条应补齐。
2. 在末尾切换文件夹、搜索和排序；确认回到顶部，无巨大空白占位。
3. 开启后台分析时滚动；确认更新不截断列表，正在看的歌曲保持位置。
4. 分别在冷/热封面缓存下往返滚动；检查文字先显示，封面能够恢复。
5. 跨未缓存区域 Shift 选择、全选、MIDI 步进、下一首及定位正在播放。
6. 关闭后恢复到深位置，并调整窗口、字号及列宽。
7. 滚动途中重启后端或断开本地服务：错误提示出现后不点重试，确认服务恢复后占位行在数秒内自行加载、提示消失。

性能目标：热缓存滚动不产生由列表代码引起的超过 50 毫秒主线程长任务；目标摘要到达后两帧内显示。实测时记录机器、Tauri 构建模式、窗口尺寸、刷新率、分析状态和缓存状态；未测量前不宣称达到该目标。
